## 23:00-31:00 | Simulation - מ-Forced I/O ועד Virtual Commissioning

**יעל:** בתעשייה משתמשים במילה Simulation לכל דבר, מ-Force ל-Input אחד ועד Digital Twin מלא. בוא נבנה סולם.

**אמיר:** רמה אפס היא **Manual Forcing או Signal Injection**. זה שימושי ב-Commissioning, אבל זה לא Model שלם כי התהליך לא מגיב דינמית. אחר כך יש **Unit-Test Harness** שמפעיל Block עם Inputs ידועים. מעליו **Software-in-the-Loop**, שבו אפליקציית הבקר רצה מול Model תוכנתי של המכונה או התהליך.

**יעל:** ואז Hardware-in-the-Loop?

**אמיר:** נכון. ב-**Hardware-in-the-Loop** הבקר הפיזי האמיתי, ולעיתים גם Interfaces אמיתיים של הרשת, עובדים מול Plant Simulated. כך בודקים Scan Timing, Drivers, Protocol Behavior ו-Controller Configuration אמיתיים בלי להפעיל את התהליך הפיזי.

**יעל:** ומה זה Virtual Commissioning?

**אמיר:** בדרך כלל זו הרצה של מערכת האוטומציה מול Model של המכונה או המפעל לפני שהציוד האמיתי מוכן. ה-Model יכול לכלול Kinematics, Sensors, Actuators, Process Dynamics, Faults ואינטראקציות מפעיל. במכונת אריזה זה יכול להיות מודל 3D פיזיקלי. בסקיד תהליכי זה יכול להיות מודל דינמי של Mass and Energy Balance. המטרה היא למצוא בעיות Integration ו-Sequence מוקדם יותר.

**יעל:** וזה אוטומטית Digital Twin?

**אמיר:** לא. "Digital Twin" הפך למונח רחב. סדרת ISO 23247 ו-IEC 62832 נותנות מסגרות מסודרות ל-Digital Twin ול-Digital Factory במערכות ייצור. אבל Model שמשמש ל-Virtual Commissioning אמין רק ביחס ל-Scope ול-Fidelity שלו. אם השסתום המדומה מגיע לפתיחה מלאה ב-200 מילישניות והשסתום האמיתי לוקח שש שניות, Sequence שעובר בסימולציה יכול להיכשל בשטח.

**יעל:** כלומר גם את ה-Model צריך לבצע עליו Validation.

**אמיר:** בדיוק. מגדירים מה הוא אמור לייצג. אם המטרה היא לבדוק Boolean Sequence Logic, אולי Fluid Dynamics מדויקים לא קריטיים. אם אנחנו מכוונים Pressure Loop, Time Constants, Dead Time, Nonlinearity ו-Actuator Limits כן קריטיים. Fidelity צריך להתאים לשאלה שהמודל אמור לענות עליה.

**יעל:** Simulation מאפשר לבדוק תקלות שיהיו יקרות או מסוכנות במערכת האמיתית.

**אמיר:** וזה אחד היתרונות הגדולים. אפשר לחזור שוב ושוב על Network Dropout, Sensor Failure, Drive Fault, Invalid Recipe, Stuck Valve, Delayed Feedback ו-Power Cycle בלי לסכן ציוד או ייצור. אפשר להאיץ זמן של Batch ארוך ולהריץ מאות תרחישי Regression בלילה.

**יעל:** אבל יש מלכודת - Pass בסימולטור יכול לייצר ביטחון מופרז.

**אמיר:** נכון. Simulation מזיזה Defects מוקדם יותר. היא לא מבטלת Site Verification. Tolerances מכניים, Cable Delays, Instrument Filtering, Topology, Friction, Backlash, Heat Loss והתנהגות מפעיל עדיין קיימים. Simulation היא שכבת ראיה - לא תחליף למציאות.

## 31:00-36:00 | FAT, FIT, SAT ו-SIT - מה כל שכבה צריכה להוכיח

**יעל:** עכשיו נמקם FAT ו-SAT בתוך ההיררכיה הזו.

**אמיר:** IEC 62381:2024 הוא Reference חשוב לתעשיית התהליך כי הוא מגדיר Requirements ו-Checklists ל-FAT, ל-**Factory Integration Test** אופציונלי, ל-SAT ול-**Site Integration Test**. בפרויקט מסוים המונחים יכולים להיות שונים, אבל ההפרדה ההנדסית שימושית מאוד.

**יעל:** מה FAT צריך להוכיח?

**אמיר:** כמה שיותר מה-Automation Specification לפני Deployment לאתר. גרסאות תוכנה, I/O Simulation, Sequences, Permissives, Alarms, HMI, Reports, Communications, Redundancy אם קיימת, Backups ו-Recovery Procedures. הרבה יותר זול לתקן Logic במפעל של האינטגרטור מאשר בזמן Shutdown באתר.

**יעל:** מה FIT מוסיף?

**אמיר:** Integration. למשל PLC, SCADA, Historian, Package Units ו-Safety System מגיעים מספקים שונים. FIT יכול להוכיח Interfaces לפני שכל האנשים והציוד מגיעים לשטח. זה חשוב במיוחד כשה-Site Schedule קצר.

**יעל:** SAT בודק את המציאות המותקנת.

**אמיר:** בדיוק. Wiring אמיתי, Instruments, כיוון Actuator, Ranges, Network Paths, Motor Rotation, Valve Action, Time Synchronization, Permissions ואינטגרציה ספציפית לאתר. SAT הוא לא רק Repeat של FAT. הוא מטפל בסיכונים שקיימים רק אחרי Installation.

**יעל:** ו-SIT?

**אמיר:** Site Integration Test מתמקד במערכת המשולבת באתר: Interfaces בין Packages, מערכות המפעל, Utilities, External Systems ולעיתים גם Operating Procedures. שוב - משתמשים במונחים שהוגדרו בחוזה ובתקן הרלוונטי.

**יעל:** מה טעות ה-FAT הכי נפוצה?

**אמיר:** לבדוק את ה-Test Script במקום את המערכת. אם הפרוצדורה אומרת "הפעל Input X ובדוק Lamp Y" אבל אף פעם לא שואלת למה Input X קורה ומה עוד חייב להיות חסום, הבדיקה הופכת לטקס. Acceptance Test טוב מבוסס דרישה וסיכון. הוא כולל Negative Tests ו-Recovery, לא רק רצף ייצור תקין.

## 36:00-38:00 | Test שנכשל הוא נכס הנדסי - אם מנהלים אותו נכון

**יעל:** מה עושים כשבדיקת FAT נכשלת? במציאות הרבה פעמים מתקנים במקום וממשיכים.

**אמיר:** לפעמים חייבים לתקן מהר, אבל הכשל צריך להפוך ל-Defect מבוקר. נותנים Identifier, Severity, שלבי Reproduction, Expected Behavior, Actual Behavior, Requirement מושפע ו-Disposition. אחרי התיקון מבצעים Retest ומחליטים איזה Regression נדרש.

**יעל:** למה לא פשוט לכתוב "תוקן" בצד של הטופס?

**אמיר:** כי אחרי חצי שנה אף אחד לא זוכר אם התיקון שינה Label אחד או Library משותפת לכל ה-Sequences. Defect Record הוא חלק משרשרת הראיות. והוא גם חושף Patterns: שוב ושוב Restart Logic, שוב Naming, שוב Timeouts. מה-Patterns האלה אפשר לשפר Architecture במקום לבצע אינסוף Patches מקומיים.

**יעל:** ומה לגבי Deviations?

**אמיר:** אם Requirement בכוונה לא מתקיים בזמן Handover, זו צריכה להיות Deviation מאושרת עם Owner, Risk, Temporary Controls אם נדרשים ו-Closure Plan. Acceptance לא אמור להסתמך על זה שכולם ישכחו בשקט מה נכשל.

## 36:00-41:00 | Regression, Versioning ואיך מוכיחים ששינוי לא החזיר תקלה

**יעל:** המכונה עובדת. אחרי חצי שנה מבקשים "שינוי קטן". שם מתחילות Regressions.

**אמיר:** נכון. מערכות תעשייתיות צוברות Behavior במשך שנים. שינוי של חמש שורות יכול להשפיע על Permissive משותף, Function Block משותף או Retained Variable שמשמש כמה Sequences. לפני השינוי צריך **Impact Analysis**: אילו Requirements, Modules, Interfaces ו-Tests יכולים להיות מושפעים?

**יעל:** ואז Version Control.

**אמיר:** Source Code, Configuration, HMI, Drive Parameters, Recipes, Network Configuration ותיעוד צריכים גרסאות או לפחות Baselines מבוקרים. Release צריך Identifier ייחודי, Change Record, Test Evidence ו-Backup שבאמת יודעים לשחזר.

**יעל:** "הגרסה האחרונה על הלפטופ של המהנדס" היא לא Release Process.

**אמיר:** בדיוק. Release טוב עונה על השאלות: מה השתנה? מי עשה Review? אילו Tests עברו? אילו Known Issues נשארו? אילו Software ו-Firmware Versions היו בשימוש? מה Rollback Plan? ואיזה קובץ בדיוק רץ עכשיו בבקר?

**יעל:** Regression Testing הוא להריץ שוב בדיקות שכבר עברו אחרי שינוי.

**אמיר:** באופן מדויק יותר - להריץ מחדש Set של בדיקות שעברו בעבר כדי לזהות Side Effects שלא התכוונו אליהם. ה-Scope צריך להיות Risk-Based. אם משנים Valve Block משותף לשישים שסתומים, Scope ה-Regression גדול בהרבה משינוי טקסט ב-HMI.

**יעל:** כאן Automation של Simulation באמת משתלם.

**אמיר:** בדיוק. Regression Suite יכול לרוץ בכל Commit או בכל Release Candidate. הוא יכול לבדוק Startup, Shutdown, Stop-Resume, Power Cycle, Communication Loss ומאות State Transitions. גם אם Vendor של ה-PLC לא תומך ב-CI/CD מודרני, אפשר לאמץ את העיקרון: Build שניתן לשחזר, Tests שחוזרים על עצמם, Artifact מבוקר ותוצאה Traceable.

**יעל:** מה שומרים אחרי FAT או Release גדול?

**אמיר:** לפחות Source ששוחרר, Artifact להורדה אם רלוונטי, גרסאות PLC ו-HMI, Configuration Exports, Test Procedures, תוצאות שבוצעו בפועל, Defect List, Deviations מאושרות, Backups ו-Release Notes. במערכות עם דרישות Cybersecurity או Functional Safety יהיו לעיתים דרישות Evidence נוספות.

## 41:00-44:00 | תוכנת Safety - אותם עקרונות, רמת משמעת גבוהה יותר

**יעל:** עד עכשיו נשארנו בעיקר ב-Basic Control. מה משתנה כשהתוכנה מבצעת Safety Function?

**אמיר:** רמת הקפדנות עולה ומחזור החיים הופך לנורמטיבי. IEC 61508-3 מגדיר דרישות Software למערכות E/E/PE Safety-Related, כולל Lifecycle Activities, Validation Information, Modification Control ו-Supporting Tools. במכונות, ISO 13849-1:2023 כולל Software בתוך תכנון SRP/CS, ו-ISO 13849-2:2012 עדיין התקן המפורסם הנוכחי ל-Validation בזמן שהמהדורה הבאה נמצאת בפיתוח. IEC 62061 במהדורה המאוחדת הנוכחית מטפל גם ב-Design, Integration, Verification, Validation ו-Configuration Management של Safety-Related Control Systems למכונות.

**יעל:** כלומר FAT כללי של ה-PLC לא מאמת אוטומטית את פונקציות הבטיחות.

**אמיר:** נכון. Safety Functions צריכות את ה-Evidence שנדרש במחזור החיים הרלוונטי: Requirements, Architecture, Assumptions של Independence, Fault Behavior, Verification ו-Validation. נעמיק בזה בפרק 13. להיום הגבול חשוב: לא משתמשים ב-Test Plan של Basic Control כתחליף ל-Safety Validation.

**יעל:** וגם לא קוראים לכל בדיקת Sequence "בדיקת Safety" רק כי בסוף המנוע נעצר.

**אמיר:** בדיוק.

## 44:00-46:00 | צ'קליסט סופי והמעבר לסייבר

**יעל:** תן את הצ'קליסט. אנחנו רגע לפני Release חדש לבקר. מה שואלים?

**אמיר:** שתים-עשרה שאלות.

1. האם הדרישות ספציפיות מספיק כדי לייצר Pass/Fail שאפשר לראות ולמדוד?
2. האם כל דרישה חשובה Traceable לקוד ולפחות ל-Test אחד?
3. האם Mode Transitions, Restart Behavior ו-Retained Data נבדקו במפורש?
4. האם בדקנו Negative Paths: Bad Quality, Timeout, Missing Feedback, Communication Loss ו-Invalid Operator Actions?
5. האם מהנדס נוסף ביצע Review לארכיטקטורה ולקוד - לא רק להתנהגות ב-HMI?
6. האם גרסת התוכנה ו-Test Environment מתועדים כך שאפשר לשחזר את התוצאה?
7. האם ה-Fidelity המיועד של ה-Simulation Model מתועד, והאם המודל עצמו הושווה למציאות במקום שבו זה נדרש?
8. האם Unit, Integration, System ו-Acceptance Tests מופרדים כך שלכל רמה יש מטרה ברורה?
9. האם FAT כלל Fault ו-Recovery Scenarios ולא רק Happy Path של ייצור?
10. האם האתר המותקן אומת מחדש ב-SAT/SIT עבור Wiring, Actuators, Networks ו-Interfaces?
11. האם לכל שינוי יש Impact Analysis, Regression Evidence, Release ID ונתיב Rollback או Restore שנבדק?
12. אם פונקציה היא Safety-Related - האם היא טופלה לפי Safety Lifecycle ולא לפי Test Plan כללי של Basic Control?

**יעל:** הסיכום שלי: איכות תוכנה היא לא תוכנית נקייה ולא קלסר FAT עבה. היא השרשרת מהדרישה עד הראיה, עם מספיק Simulation ו-Testing כדי ששינוי עתידי יהיה צפוי.

**אמיר:** בדיוק. המטרה היא לא לטעון שאי אפשר שיהיו Bugs. המטרה היא למצוא אותם מוקדם יותר, לשחזר כשל מהר יותר ולהכניס שינויים בצורה בטוחה יותר.

**יעל:** והבעיה הבאה היא שגם תוכנה שנבדקה בצורה מושלמת יכולה להשתנות על ידי האדם הלא נכון, דרך נתיב הרשת הלא נכון ובזמן הלא נכון.

**אמיר:** וזה לוקח אותנו לפרק 12: **Industrial Cybersecurity**. Zones and Conduits, Identities, Remote Access, Secure Development, Patching, Backups, Incident Response ומחזור החיים של IEC 62443.

**יעל:** עד אז, אל תשאלו רק "האם הבדיקה עברה?". תשאלו "איזו דרישה היא הוכיחה, באילו תנאים, והאם נוכל להוכיח אותה שוב מחר?"

**אמיר:** תודה שהאזנתם ל-Control Edge.
