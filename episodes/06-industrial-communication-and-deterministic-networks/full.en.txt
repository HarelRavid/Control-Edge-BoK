4. Industrial communication architecture map

| Layer / stage | Engineering decision | Typical failure |

| 1. Application requirement | Define traffic class, deadline, update period, data age, loss response and availability. | Selecting a protocol before defining the physical consequence of delay. |
| 2. Physical medium | Choose copper, fiber, serial bus, SPE/APL, connector, distance, environment and grounding. | Intermittent errors, EMC sensitivity, excessive stubs or unsuitable connectors. |
| 3. Data link and switching | Define topology, duplex, VLAN, queues, multicast, forwarding and redundancy. | Bursts fill queues; multicast floods devices; hidden line dependencies. |
| 4. Network and transport | Decide local Layer 2, routing, TCP, UDP and addressing boundaries. | Variable retransmission delay, duplicate addressing or unintended routed paths. |
| 5. Application profile | Select services, device profiles, diagnostics, conformance and engineering tools. | Bits transfer, but state, units, timing or fail behavior do not interoperate. |
| 6. Time and scheduling | Define clock profile, timestamping, execution model, offset limits and alarms. | Messages arrive but coordinated devices execute against different time bases. |
| 7. Availability | Specify tolerated faults, maximum recovery, output behavior and repair strategy. | A ring exists, but recovery exceeds watchdog or both paths share one cause. |
| 8. Lifecycle and evidence | Control configuration, firmware, backups, monitoring, captures and acceptance tests. | The network works initially but cannot be reproduced, diagnosed or secured. |

| PROFINET RT / IRT | Distributed I/O, drives and machine automation in the PI ecosystem. | Required conformance class, cycle, synchronization, topology and device certification? |

| TSN-profiled converged Ethernet | Mixed time-sensitive and ordinary traffic on engineered common infrastructure. | Which 802.1 features, IEC/IEEE 60802 profile, configuration model and conformance evidence? |

Core principle \| A control network is accepted by the physical behavior it preserves under defined load and faults - not by link speed, a protocol logo, a successful ping or an empty-network benchmark.

7. Full episode script

00:00-03:00 | Cold open - the network that passes every ping test

Yael: The packaging cell runs perfectly for several minutes. Then the vision system uploads a burst of images, a remote I/O rack reports a timeout, and two servo axes arrive a few milliseconds apart. Maintenance pings every device and gets clean replies. Their conclusion is that the network is healthy.

Amir: A successful ping proves only that an IP path answered a small diagnostic request. It does not prove that cyclic control data arrived inside its required time window, with acceptable jitter, in the correct order, or synchronized to the same clock.

Yael: So the network can be connected and still be unfit for control.

Amir: Exactly. In office networking, a delayed file is annoying. In a machine, a delayed output can change a physical event. The network is not merely transporting information; it may be carrying part of the control loop.

Yael: The image transfer suggests bandwidth congestion, but the axis mismatch sounds like a timing problem.

Amir: Those may be connected, but we must not jump straight to 'buy a faster switch.' We need to identify the traffic classes, the timing contract for each class, the topology, the queueing behavior, the synchronization method, and what every device does when a deadline is missed.

Yael: Today we will separate bandwidth, latency, jitter, synchronization and availability, then compare fieldbus, Industrial Ethernet and TSN without turning protocol names into a league table.

Amir: And at the end we will return to the packaging cell with evidence, not folklore.

03:00-06:30 | The network is part of the machine architecture

Yael: Where should a mechanical or process engineer draw the network on the system diagram?

Amir: Between every producer and consumer of control information. A sensor may publish a measured value, a controller computes a command, a drive receives a setpoint, and an HMI requests diagnostics. The network connects those functions, but each exchange has a different consequence if it is late or lost.

Yael: We therefore start from data classes rather than from a protocol brand.

Amir: Yes. Classify cyclic I/O, motion setpoints, safety messages, alarms, recipes, engineering downloads, historian traffic, video and maintenance access. Then define update period, maximum age, allowable jitter, loss behavior, recovery time and required availability for each class.

Yael: Is update period the same as latency?

Amir: No. A controller may produce a value every one millisecond, while the end-to-end latency from sampling to actuation is several milliseconds. Jitter is the variation around that latency. Data age also includes waiting before transmission and waiting until the receiving task uses the value.

Yael: That connects directly to Episode 2. A fast network cannot compensate for a slow PLC task.

Amir: Correct. End-to-end response is sensor conversion, input update, network transport, task scheduling, logic execution, output update and actuator response. Optimizing one link without measuring the chain can create impressive specifications and poor machine behavior.

Yael: What is the first architecture question?

Amir: Who owns time. Does the controller poll devices, do devices produce data periodically, do all nodes share a clock, or does the receiver act on timestamps? The answer determines how we reason about determinism.

06:30-10:30 | Layers: cable, Ethernet, IP and the automation protocol

Yael: Engineers often say 'it is Ethernet' as if that describes the whole system.

Amir: Ethernet mainly defines lower-layer framing and media behavior. Above it may sit IP, UDP or TCP, and above those an industrial application protocol. Some real-time protocols use standard Ethernet frames but bypass TCP/IP for cyclic traffic. Others use UDP with synchronized end devices. EtherCAT processes a dedicated Ethernet frame on the fly through its nodes.

Yael: So an RJ45 connector does not tell me how the control data behaves.

Amir: Nor does a one-gigabit link. You must know the physical medium, duplex mode, switch architecture, VLAN and priority configuration, multicast behavior, transport mechanism, application profile and device implementation.

Yael: Explain MAC address and IP address in practical terms.

Amir: A switch forwards Ethernet frames mainly by MAC address within a Layer-2 domain. An IP address supports routed communication across Layer-3 networks. Routing is valuable for segmentation and scale, but many cyclic industrial exchanges are designed around a local switched domain or require explicit engineering when routed.

Yael: Where do TCP and UDP fit?

Amir: TCP provides ordered, reliable byte streams using acknowledgements and retransmission. That is useful for configuration, files and many client-server services, but retransmission introduces variable delay. UDP is connectionless and avoids that mechanism; the application must decide how to detect loss, sequencing and freshness.

Yael: And a fieldbus profile standardizes more than a packet format.

Amir: Ideally it defines services, device behavior, state machines, timing and conformance expectations. IEC 61158 contains fieldbus specifications, while IEC 61784 organizes communication profiles. Those families are large because industrial interoperability requires more than agreeing on bits on a wire.

Yael: This is why a gateway can translate registers but still lose diagnostics or timing semantics.

Amir: Exactly. Protocol conversion is not automatically behavior preservation.

10:30-14:30 | Real time means a bounded result, not merely a small average

Yael: People describe any fast network as real time. What definition should we use?

Amir: A useful engineering definition is that the required communication action completes within a specified time window with defined confidence. The deadline comes from the application. A temperature loop may tolerate hundreds of milliseconds; coordinated motion may require synchronized updates with microsecond-level clock agreement.

Yael: Which performance numbers belong in a requirement?

Amir: Cycle or update time, end-to-end latency, jitter, synchronization accuracy, packet loss, startup time, recovery time after a fault, and data-age limits. Also network load under normal, peak and failure conditions.

Yael: Why is average latency dangerous?

Amir: Because a machine fails on the tail of the distribution. An average of half a millisecond can hide occasional ten-millisecond delays. We need maximum observed values under defined load, or a defensible bound, plus counters that reveal discarded or late frames.

Yael: Is determinism the same as no packet loss?

Amir: No. Determinism concerns predictable timing and behavior. A system can deterministically declare a timeout and move to a safe state. Conversely, a network can lose no packets during a short test yet have unbounded queueing delay under a traffic burst.

Yael: What about bandwidth utilization?

Amir: It matters, but percentage alone is insufficient. A low average load can contain bursts that fill queues. A large non-preemptable frame can block an urgent frame. Multicast can be replicated to many ports. We need traffic shape and queue behavior, not just megabits per second.

Yael: Then the acceptance test must create worst credible traffic, not an empty network.

Amir: Yes, including engineering downloads, camera bursts, historian queries, device replacement, link failure and controller switchover where applicable.

14:30-18:30 | Why fieldbus still exists

Yael: If Industrial Ethernet is so capable, why do plants still use serial and CAN-based fieldbuses?

Amir: Because mature fieldbuses can be simple, robust and well matched to the process. A two-wire multidrop network may be ideal for a modest number of instruments over long distance. CAN-based systems provide arbitration and compact frames. Existing plants have trained staff, spare parts and validated designs.

Yael: Modbus RTU is often called primitive.

Amir: It is simple, not self-describing. A master requests coils or registers and the engineer must know what each address means, how values are scaled, byte order, timeout and exception behavior. That simplicity can be an advantage for a small, slow exchange, but it transfers semantic responsibility into drawings and software.

Yael: What are the common engineering mistakes?

Amir: Wrong termination, star wiring on a bus that expects a line, excessive stubs, missing biasing, duplicate addresses, mismatched baud or parity, poor shielding, and timeouts chosen without calculating the full poll cycle.

Yael: The poll cycle becomes longer as devices and retries are added.

Amir: Exactly. A value may be physically updated quickly but read only once per second because the master is servicing many devices. The HMI may display it as current unless the application carries a timestamp or quality flag.

Yael: So migration should not be justified only by speed.

Amir: Correct. Migrate for lifecycle, diagnostics, data volume, maintainability, integration or availability. A functioning fieldbus should not be replaced casually, but neither should brownfield familiarity prevent an architecture that the new machine genuinely needs.

Yael: And installation remains a physical discipline.

Amir: IEC 61918 and the IEC 61784-5 installation profiles are reminders that topology, cabling, connectors, separation, grounding and verification are part of communication engineering.

18:30-24:00 | Industrial Ethernet families are different architectures

Yael: Let us compare the major families without declaring a universal winner.

Amir: Start with Modbus TCP. It maps the familiar Modbus application model onto TCP/IP. It is widely implemented and useful for straightforward request-response integration, but the protocol by itself is not a coordinated-motion timing architecture.

Yael: PROFINET uses several communication channels.

Amir: Standard TCP/IP handles non-time-critical services. PROFINET RT sends cyclic real-time frames without the TCP/IP path for typical automation. PROFINET IRT adds synchronized scheduling mechanisms for demanding isochronous applications. The required conformance class and performance must be specified, not assumed from the word PROFINET.

Yael: EtherNet/IP uses CIP at the application layer.

Amir: Yes. It supports explicit messaging and cyclic I/O, usually with UDP for produced and consumed data. CIP Sync provides precision time, and CIP Motion uses synchronized, timestamped behavior so end devices can execute coordinated motion without requiring every frame to arrive at an identical instant.

Yael: EtherCAT takes another approach.

Amir: The MainDevice sends a frame through the segment, and SubDevices read and insert process data as it passes. Hardware processing and distributed clocks make timing predictable and efficient, which is attractive for dense I/O and motion. It is Ethernet-based, but its segment behavior is not the same as a conventional switched TCP/IP network.

Yael: What about POWERLINK, Sercos and CC-Link IE TSN?

Amir: They are additional established ecosystems with their own scheduling, profiles and conformance structures. The lesson is not to memorize a ranking. It is to match application timing, topology, device availability, engineering tools, safety profile, diagnostics, lifecycle and team capability.

Yael: Does one machine need one protocol?

Amir: Not necessarily. A motion bus may serve axes and I/O, while OPC UA exposes structured information upward. A gateway may connect a legacy instrument bus. But every boundary must define ownership, data quality, time and failure behavior.

Yael: How should vendor preference be handled?

Amir: As a legitimate lifecycle constraint, not as proof of technical superiority. Installed base, local support, spare strategy and engineering competence can dominate the total cost of a theoretically faster protocol.

Yael: Conformance testing matters too.

Amir: Very much. A specification creates possibility; certified or conformance-tested products and system-level commissioning create confidence.

24:00-28:00 | Cyclic, acyclic, client-server and publish-subscribe

Yael: We have used many communication patterns. Can we organize them?

Amir: Cyclic data is exchanged at a configured period, typically for process I/O. Acyclic services carry parameters, alarms, identification and diagnostics when needed. Client-server means one side requests a service and receives a response. Producer-consumer or publish-subscribe allows one producer to distribute data to one or more consumers.

Yael: Is publish-subscribe automatically real time?

Amir: No. It describes an interaction pattern, not a timing guarantee. Real-time behavior depends on transport, scheduling, network configuration, endpoints and the profile used.

Yael: OPC UA is often described as the universal answer.

Amir: OPC UA provides a rich information model, services, security model and multiple transport mappings. It is excellent for semantic interoperability. OPC UA PubSub and the UAFX work extend it toward field-level exchanges, but engineers must specify the exact profile, interaction and performance rather than using 'OPC UA' as a timing claim.

Yael: Why are semantics important for mechanical and process engineers?

Amir: A number without engineering unit, status, timestamp, range and identity is fragile. Semantic models can state that a value is discharge pressure in kilopascals with quality and device context, rather than register 40127 multiplied by 0.1.

Yael: Yet richer models can create more configuration.

Amir: Yes. Interoperability needs agreed companion specifications, device profiles and naming discipline. A flexible model used inconsistently can be harder to integrate than a simple map used carefully.

Yael: Safety communication uses another layer of discipline.

Amir: IEC 61784-3 describes functional-safety communication profiles using the black-channel approach. Safety integrity is provided by the safety layer's measures and validated endpoints, not by assuming the ordinary network is fault-free. That does not remove the need to engineer availability and security of the underlying network.

28:00-32:30 | Topology, switches and traffic engineering

Yael: The packaging cell uses a line topology through device ports, then an unmanaged switch connects the camera and HMI. What should we inspect?

Amir: First draw the actual physical and logical topology. Device ports may contain an internal switch. A line of twenty devices creates propagation and per-device forwarding paths. A single power loss can open the line unless the architecture includes a ring or alternate path.

Yael: When is a managed switch justified?

Amir: Whenever you need evidence and control: port statistics, topology discovery, VLANs, priority queues, multicast management, port mirroring, redundancy protocols, time synchronization support, access control or alarms. An unmanaged switch can be acceptable in a simple isolated cell, but its behavior is harder to verify and diagnose.

Yael: Explain VLAN and priority without turning this into an IT course.

Amir: A VLAN separates Layer-2 broadcast domains logically. Priority marking places frames into traffic classes, but priority works only if every bridge is configured consistently and the queues are engineered. Priority is not reserved bandwidth, and low-priority traffic can still matter if buffers or links saturate.

Yael: What about multicast?

Amir: Producer-consumer protocols may use multicast. Without IGMP snooping or protocol-specific controls, a switch may flood multicast to ports that do not need it. That wastes bandwidth and can overload small device interfaces. Incorrect filtering can also suppress required traffic.

Yael: Could the camera burst fill a queue even on a gigabit uplink?

Amir: Yes, especially where traffic converges onto a slower hundred-megabit link or a device with shallow buffers. Speed transitions, asymmetric traffic and microbursts matter. A packet capture at one location may miss the congested queue elsewhere.

Yael: Copper versus fiber?

Amir: Choose for distance, EMC environment, grounding strategy, connector robustness, bend radius, maintenance and hazardous-area requirements. Fiber breaks galvanic paths and supports distance, but connectors and cleaning require discipline. Ethernet-APL is another physical-layer option for process plants: two-wire, loop-powered 10BASE-T1L with extensions for long reach and hazardous areas.

Yael: So media selection is an engineering decision, not a procurement afterthought.

Amir: Exactly.

32:30-36:30 | Time synchronization changes the control model

Yael: Why synchronize clocks if the network already sends data quickly?

Amir: Because synchronized devices can measure and act against a common time base. A sample can carry the time it was acquired, and axes can execute commands at a scheduled instant. This separates execution accuracy from variable arrival time within an allowed window.

Yael: Is that what PTP provides?

Amir: IEEE 1588, adopted internationally as IEC 61588, defines Precision Time Protocol. Profiles select options for specific industries. IEEE 802.1AS defines timing and synchronization for time-sensitive bridged networks. Industrial protocols may use these concepts or their own distributed-clock mechanisms.

Yael: What hardware is required?

Amir: The accuracy depends on timestamping location, oscillator quality, bridge support, path-delay measurement, topology and profile configuration. Hardware timestamping near the physical interface can remove variable software delay. A normal software clock sync is not automatically adequate for motion.

Yael: How do we verify synchronization?

Amir: Check grand clock selection, domain and profile, offset, path delay, role changes, holdover behavior and alarms. Then verify the physical result with synchronized traces or measurement equipment. A screen showing 'locked' is not the acceptance criterion.

Yael: What happens if time becomes wrong but communication remains active?

Amir: That can be more dangerous than a clean disconnect. The design needs limits for acceptable time error, detection of time-quality degradation, and defined response. Time is a controlled resource, not background plumbing.

Yael: In our cell, the axes may receive all setpoints yet execute them against clocks that are no longer aligned.

Amir: Precisely. We must look at both message delivery and clock health.

36:30-40:00 | Redundancy is a recovery-time requirement

Yael: Plants often request a redundant ring. Is that enough as a specification?

Amir: No. Define which single faults must be tolerated, whether communication may be interrupted, maximum recovery time, what happens to outputs during recovery, and how the fault is alarmed and repaired.

Yael: Compare common approaches.

Amir: Spanning-tree variants prevent loops but may recover too slowly or variably for some control applications. Industrial ring protocols such as MRP or DLR are engineered for defined topologies and faster recovery. PRP and HSR send duplicate frames over redundant paths and can provide seamless switchover with zero recovery time for a single network failure, at the cost of duplicated infrastructure and compatible nodes.

Yael: Redundancy can create new common-cause failures.

Amir: Yes. Two cables in the same tray, two switches on one power supply, or two logical paths through one physical choke point are not independent. Configuration errors can also disable both paths simultaneously.

Yael: How should controller and network redundancy interact?

Amir: They need one system sequence. Controller switchover, connection re-establishment, ownership of outputs, time synchronization and device watchdogs must be tested together. Network recovery that is faster than the device timeout may be invisible; slower recovery may trigger a safe or stopped state.

Yael: Availability is not safety.

Amir: Correct. Redundancy can reduce nuisance stops, but a dangerous command duplicated perfectly is still dangerous. Functional safety, cybersecurity and availability are different properties that must be coordinated.

Yael: And the proof is a fault-injection test.

Amir: Pull the specified link, power the specified switch off, disturb the clock source, replace a device, and measure the actual response under load.

40:00-43:00 | TSN: a toolbox and now an industrial profile

Yael: Time-Sensitive Networking is presented as the network that will unify everything. What is it actually?

Amir: TSN is a family of IEEE 802.1 mechanisms for time synchronization, scheduled traffic, traffic shaping, frame preemption, per-stream filtering and policing, redundancy and centralized configuration. It is not one protocol and not an automation information model.

Yael: So buying a switch with a TSN logo does not create an interoperable control system.

Amir: Correct. Devices must implement compatible features, profiles, configuration models and timing assumptions. That is why IEC/IEEE 60802 is important: the 2026 industrial automation profile selects features, options and procedures for bridges, end stations and LANs.

Yael: Give examples of the toolbox.

Amir: IEEE 802.1AS provides a common time base. Scheduled traffic can open and close transmission gates according to time. Frame preemption reduces the blocking effect of a long lower-priority frame. Per-stream filtering and policing can contain misbehaving traffic. Frame replication and elimination can improve reliability.

Yael: Does TSN replace PROFINET, EtherNet/IP or OPC UA FX?

Amir: Not by itself. It can provide a converged Ethernet foundation that industrial protocols and information models use. Protocol organizations define how their application services, engineering workflows and conformance fit that foundation.

Yael: What is the practical status for an engineer today?

Amir: Treat TSN as a maturing, standards-based capability. Specify products and profiles that are actually supported and tested, not future-roadmap promises. The publication of IEC/IEEE 60802 is a major milestone, but system interoperability still depends on implementation and conformance.

Yael: And UAFX is moving OPC UA toward field exchange.

Amir: Yes, with current releases focused strongly on controller-to-controller interactions and a broader field vision. Again, select the exact released profile and test the intended use case.

43:00-45:00 | Resolve the packaging-cell fault and close

Yael: We return to the packaging cell. The packet capture shows no link loss. During every image burst, the unmanaged switch forwards camera traffic into the same hundred-megabit device line. The egress queue fills, cyclic frames become late, and one remote I/O watchdog expires.

Amir: The motion issue has a second cause. One replacement drive was commissioned without the required time-synchronization profile. It receives commands, but its clock offset grows until coordinated execution exceeds tolerance.

Yael: The corrective action is therefore not simply a faster switch.

Amir: We separate camera and control traffic logically and physically where appropriate, use managed industrial infrastructure, configure the required real-time profile and multicast behavior, restore the drive's synchronization configuration, and define alarms for queue drops, late packets and clock offset.

Yael: Then we repeat the test with worst-case image transfer, engineering traffic and a ring fault.

Amir: And trend end-to-end evidence: controller task timing, protocol diagnostics, switch counters, watchdog events, clock quality and physical axis error. The network is accepted only when the machine behavior remains within its requirement.

Yael: What should the listener remember?

Amir: First, connected is not deterministic. Second, bandwidth, latency, jitter, synchronization and recovery are different requirements. Third, protocol selection begins with the application and lifecycle. Fourth, topology and installation are part of the control design. Fifth, every fault response must be defined and tested.

Yael: In the next episode we move above the network into PLC programming languages and software architecture: how Ladder, Structured Text, function blocks, state machines and reusable modules turn requirements into maintainable code.

Amir: Because a perfectly deterministic network can still deliver a badly designed command exactly on time.

8. Producer and host notes

- Keep the physical consequence of late or stale data visible throughout the conversation.

- Do not use bandwidth, latency, jitter, synchronization and determinism as synonyms.

- Avoid claiming that one Industrial Ethernet family is universally faster or better.

- When mentioning numerical protocol performance, frame it as profile- and implementation-dependent rather than a universal system guarantee.

- Explain that a gateway may preserve values while losing state, diagnostics, timestamps or failure semantics.

- Do not imply that VLAN or priority alone reserves bandwidth or creates determinism.

- Make the boundary between availability, functional safety and cybersecurity explicit.

- Do not read standard numbers in the dialogue except IEC/IEEE 60802 near the TSN segment.

- Keep the second cause of the packaging fault - incorrect clock profile - hidden until the final segment.

9. Engineering network checklist

1. What physical action depends on each communication flow, and what happens if the data is late, stale, duplicated or lost?

1. What are the required update period, maximum end-to-end latency, jitter, synchronization accuracy and data-age limit?

1. Which flows are cyclic I/O, motion, safety, alarms, engineering, historian, video or maintenance?

1. Which protocol profile, device class and conformance evidence are required - not just which protocol name?

1. What physical medium, connector, distance, topology, environmental rating and grounding method are appropriate?

1. Where are speed transitions, traffic convergence points, queues and low-capacity device interfaces?

1. How are VLANs, priority, multicast, IGMP and routing engineered and documented?

1. Who owns time, what clock profile is used, and what offset or time-quality limit triggers action?

1. Which single faults must be tolerated, what is maximum recovery time, and what happens to outputs during recovery?

1. Are redundant paths independent in cable route, power, switching, configuration and clock source?

1. What switch, controller and protocol counters are collected, alarmed and historized?

1. How are configuration, firmware, certificates, device descriptions and backups version-controlled?

1. What worst-case traffic and fault-injection tests prove performance before release?

1. What changes trigger revalidation: device, switch, topology, camera, firmware, task time, protocol profile or traffic load?

10. Glossary

| Term | Meaning in this episode |

| Bandwidth | Maximum data-carrying capacity of a link; not a timing guarantee. |
| Latency | Time taken for information to travel from a defined source event to a defined destination event. |
| Jitter | Variation in latency, cycle timing or execution timing. |
| Data age | Elapsed time between physical acquisition or production of a value and its use. |
| Determinism | Predictable bounded timing and defined behavior under stated conditions. |
| Cyclic I/O | Process data exchanged repeatedly at a configured interval. |
| Acyclic service | On-demand configuration, alarm, identification or diagnostic exchange. |
| PTP / Precision Time Protocol | Clock synchronization protocol standardized by IEEE 1588 and IEC 61588. |
| Distributed clocks | Architecture that aligns local device clocks for synchronized sampling or execution. |
| VLAN | Logical Layer-2 segmentation and tagging mechanism within bridged networks. |
| QoS / priority | Traffic classification and queue treatment; not automatically reserved bandwidth. |
| Multicast | One sender distributes frames to a group of receivers. |
| MRP / DLR | Industrial ring recovery mechanisms associated with particular ecosystems and topologies. |
| PRP / HSR | Seamless redundancy protocols using duplicate paths and frame elimination. |
| TSN | Family of IEEE 802.1 mechanisms for time-sensitive bridged networking. |
| OPC UA FX / UAFX | OPC UA Field eXchange specifications extending OPC UA toward field-level interactions. |
| Ethernet-APL | Two-wire, loop-powered 10BASE-T1L physical layer with process-industry extensions. |
| Black channel | Functional-safety communication concept in which safety measures are implemented independently of assumptions about the ordinary transmission channel. |

12. Episode quality gate

- The listener can draw a layered end-to-end communication architecture.

- Bandwidth, latency, jitter, synchronization, data age and recovery time are clearly distinguished.

- Fieldbus and Industrial Ethernet are compared by requirements and architecture rather than popularity.

- Topology, switching, multicast, media and installation are treated as control-design decisions.

- Time synchronization is explained as a controlled resource with health and failure limits.

- Redundancy is specified through tolerated faults and recovery behavior, not merely a ring drawing.

- TSN is presented as an IEEE toolbox and IEC/IEEE 60802 as an industrial profile.

- The closing diagnosis resolves both congestion and clock-offset symptoms.

- The ending creates a clean bridge to PLC languages and maintainable automation software.
